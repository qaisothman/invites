# Production readiness

Invites runs locally by design ([run and test it](00-run-and-test-locally.md)). This review lists what would have to be true before it served real members, with every line checked against evidence. "Done" means the evidence exists in this repository today. "Open" names the work and a rough estimate. In production it would be run again at each [trigger](#when-to-run-it-again).

## The gate

| # | Item | Status | Evidence, or the work left |
|---|---|---|---|
| 1 | Design written down: brief, architecture, data model, SLOs | Done | [Product brief](01-product-brief.md), [architecture](02-architecture.md), [data model](03-data-model.md), [SLOs and alerts](06-slos-and-alerts.md), [ADRs](adr/) |
| 2 | One member can't read, answer or cancel another's invitations, or remove another's phone | Done | `invitations.e2e-spec.ts`: "shows an invitation only to the two people involved" and "lets only the invitee answer, the inviter cancel and the owner remove a phone". Every route needs a session unless marked `@Public()`: a global guard (`app.module.ts`, `guards.ts`); `auth.e2e-spec.ts` checks it on `/users/me` |
| 3 | Rate limits on everything that sends | Done | 30 invitations per member an hour (`INVITES_PER_HOUR`), 10 requests a minute per IP to sign-up and to sign-in (`AUTH_PER_MINUTE`; refresh and sign-out carry a 256-bit token and fall under the default), 120 requests a minute per member on each route (per IP when signed out), one invitation email per person a day (held in the database). `rate-limit.e2e-spec.ts` checks the sign-in and invitation limits. The per-IP limits read the client's address through `TRUST_PROXY_HOPS`: 0 when clients connect directly, 1 behind one load balancer; production refuses to boot until it is set. The three request limits are counted per API instance, so with stage 0's two instances each must be set to half the intended value ([scaling plan](04-scaling-plan.md#stage-0-launch-up-to-10000-members)) |
| 4 | No secret in the code or the image | Done, scanning open | Every secret comes from the environment and is checked at boot (`env.validation.ts`); the only values committed are local placeholders (`api/.env.example`, `docker-compose.yml`, test and bench setup); `.env` is ignored by git and Docker. **Open:** a secret scanner in CI (gitleaks or GitHub's push protection), and a boot check that refuses the committed placeholder `JWT_SECRET` in production, 1 hour |
| 5 | Logs: one line per request, carrying a JSON object with its request id; no push tokens, ack tokens or unsubscribe signatures | Done | `request-id.middleware.ts` logs the path without its query string; ack tokens travel in request bodies; `LogEmailSender` masks the address and cuts the unsubscribe token everywhere, and in production logs only the masked address and the subject |
| 6 | Errors reach a person, tagged by release | Open | Sentry on the API and the app, tagged by API image and EAS update id. Half a day |
| 7 | One alert pages a phone | Open | The rules exist, each linked to its runbook section ([ops/alerts.yml](../ops/alerts.yml)). **Open:** Alertmanager routed to a pager, plus an external uptime check on `/health/ready`, tested with a real page; and the dashboards and the daily query for the two delivery SLOs in [SLOs and alerts](06-slos-and-alerts.md). Half a day, after hosting |
| 8 | Deploy and roll back with one command | Open | One image in three roles, release order and rollback written down ([releases](07-release-and-migrations.md)). **Open:** the pipeline on the chosen host, and one rehearsed rollback each of the API image and an `eas update`; `/metrics` closed to the internet at the load balancer. 1 day, after hosting |
| 9 | Backups that have been restored | Open | Managed Postgres with point-in-time recovery, and one restore to a new instance, timed and written down. Half a day, after hosting |
| 10 | Health checks, clean shutdown, timeouts | Done | `/health/live` and `/health/ready`; SIGTERM lets workers finish their batch (`worker-runner.ts`); 10-second timeout on Expo calls, and a 40-second send deadline per batch inside its 60-second lease; 15-second statement timeout in Postgres |
| 11 | Account deletion in the app | Open | Apple requires it for apps with sign-up (App Review Guideline 5.1.1(v)). `DELETE /users/me` removing sessions, devices, invitations and notifications, with indexes on `devices (user_id)` and `push_tickets (device_id)` for the cascade, and a button in Profile; Google Play also requires a web page to request deletion. 1 to 2 days |
| 12 | Report and block | Open | The invitation message is text one member writes to another. Apple's Guideline 1.2 asks apps with user-generated content for a filter for objectionable text, a way to report it with a timely response, a way to block abusive users, and published contact details; Google Play also requires in-app reporting. Display names are member-written too, so some of this applies either way: they refuse links (`http:`, `https:`, `www.` or a domain followed by a path, full-width look-alikes included), control characters, line breaks and characters that hide or reorder text, and accept a bare domain (`evil.example`) and dotted names (`J.Smith`). Build it (2 to 3 days), or leave the free-text message out at first to shrink it ([what production would take](12-what-production-would-take.md#decisions-production-would-need)) |
| 13 | Privacy paperwork | Open | Record of processing, retention schedule (13 months of notifications, [data model](03-data-model.md#growth-and-retention)), processor agreements, privacy notice with a complaints route. Listed in [Sending real email, section 5](08-sending-real-email.md#5-terms-privacy-notice-and-law). A few hours with whoever owns legal |
| 14 | Production push credentials | Open | An APNs key for production builds and Firebase credentials for Android, uploaded to EAS; one push checked on each platform from a production build. Half a day |
| 15 | Real email | Open | Everything in [Sending real email](08-sending-real-email.md): the provider and domain authentication (a day), verifying the address at sign-up (a day), bounce and complaint webhooks (a day), and the link domain (a day): the real domain in `APP_LINK_BASE` and `app/app.config.ts`, `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` served from it, and the page at `/i/<id>` for people without the app. Warm-up runs alongside the rest |
| 16 | Old apps can be told to update | Open | Phased release turned on in both stores, and a minimum supported version: the app sends its version, and the API answers `426` below it so the app shows "please update". Half a day |

Done: 6 of 16. The 10 open items are deliberate: none is needed to run Invites locally. They are one engineer's work: about 12 working days once hosting is chosen (a day or two fewer if the free-text message waits for a later release), plus 1 to 2 days to set hosting up, plus email warm-up, which runs alongside.

## When to run it again

| Trigger | What gets added |
|---|---|
| Around 1,000 weekly actives, or the first revenue | Error budgets reviewed monthly, an on-call rotation of at least two people, a restore drill every quarter |
| A fundraise, an enterprise customer's security questionnaire, or 10 times the traffic | An external penetration test, canary releases, a disaster-recovery drill |
| A new channel or a new kind of notification | Rows 3, 5 and 13 for that channel, and an ADR |
